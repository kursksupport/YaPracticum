Описание API

Проект содержит REST API для работы с мероприятиями

Используемые технологии

C#
.NET 9
ASP.NET Core Web API
Entity Framework Core
PostgreSQL
Swagger

Структура проекта
Проект разделен на несколько слоев по принципам Clean Architecture:
EventManagementService — Presentation слой
Содержит:
контроллеры API;
middleware обработки ошибок;
настройку DI и запуск приложения.
Отвечает только за обработку HTTP-запросов и возврат ответов.
EventManagementService.Application — слой бизнес-логики
Содержит:
сервисы приложения (use cases);
интерфейсы репозиториев;
DTO;
интерфейсы внешних зависимостей.
Application не зависит от Infrastructure и работает только через интерфейсы
EventManagementService.Domain — доменный слой
Содержит:
сущности Event и Booking;
перечисления;
доменные исключения.
Domain не зависит от других слоев и внешних технологий
EventManagementService.Infrastructure — инфраструктурный слой
Содержит:
DbContext;
реализации репозиториев;
конфигурации Entity Framework Core;
миграции базы данных
Infrastructure реализует интерфейсы, которые определены в Application

Эндпоинты
Регистрация пользователя
POST /auth/register
Регистрирует нового пользователя.
По умолчанию назначается роль User.
При успешной регистрации возвращается 204 No Content.
Получение JWT-токена
POST /auth/login
Проверяет логин и пароль пользователя и возвращает JWT-токен.
При неверных учётных данных возвращается 400 Bad Request.
Отмена брони
DELETE /bookings/{id}
Отменяет бронирование.
Пользователь может отменить только собственную бронь.
Администратор может отменить любую бронь.
При отсутствии прав возвращается 403 Forbidden.
При успешной отмене возвращается 204 No Content.
Получить список всех мероприятий
GET /events
Возвращает все созданные мероприятия
Получить мероприятие по Id
GET /events/{id}
Возвращает одно мероприятие по его Id
Если мероприятие не найдено — возвращается 404 Not Found
Создать мероприятие
POST /events
Создает новое мероприятие
При успешном создании возвращается 201 Created
Обновить мероприятие
PUT /events/{id}
Полностью обновляет мероприятие по Id
Если мероприятие не найдено — возвращается 404 Not Found
Удалить мероприятие
DELETE /events/{id}
Удаляет мероприятие по Id
Если мероприятие не найдено — возвращается 404 Not Found
При успешном удалении возвращается 204 No Content


Модель Event
Событие содержит следующие ключевые поля:
TotalSeats — общее количество мест (обязательное при создании)
AvailableSeats — текущее количество доступных мест
Поведение:
при создании:
AvailableSeats = TotalSeats
при бронировании:
уменьшается на 1
при отмене брони:
может быть увеличено обратно

Создание брони
POST /events/{id}/book
Создает новую бронь для указанного мероприятия
Если бронь успешно создана — ответ 202 Accepted
Если мероприятие не найдено — 404 Not Found
Нет доступных мест — 409 Conflict

Получение брони
GET /bookings/{id}
Возвращает информацию о брони по её идентификатору
Если бронь найдена — 200 OK
Если бронь не найдена — 404 Not Found
Проверяются следующие правила:
поле Title обязательно;
поля StartAt и EndAt обязательны;
EndAt должно быть позже StartAt.

Фоновая обработка
После создания бронь получает статус Pending
Фоновый сервис периодически проверяет наличие необработанных броней
Для каждой брони выполняется искусственная задержка 2 секунды, после чего статус изменяется на Confirmed и заполняется поле ProcessedAt

Пример использования
Создать мероприятие через POST /events
Создать бронь через POST /events/{id}/book
Получить бронь через GET /bookings/{id}
Сразу после создания статус будет Pending.
Через несколько секунд статус изменится на Confirmed.

Сценарий овербукинга
Событие:
2 места
Параллельные запросы:
5 пользователей вызывают POST /events/{id}/book
Результат:
2 брони — успешно (Pending, Confirmed)
3 брони — 409 Conflict

Потокобезопасность и защита от овербукинга
Для предотвращения ситуации, когда несколько пользователей одновременно бронируют последние места, реализована синхронизация критической секции
SemaphoreSlim
Используется в BookingService
Назначение:
гарантирует, что только один поток одновременно резервирует место;
предотвращает состояние гонки;
позволяет безопасно использовать await внутри критической секции.
SemaphoreSlim в фоновом сервисе
Используется в сервисе обработки бронирований
Назначение:
синхронизирует параллельную обработку броней;
предотвращает одновременное изменение состояния одной и той же записи

Фильтрация и пагинация
Поддерживаются параметры:
title
Поиск по названию события (частичное совпадение)
from
События начинаются не раньше указанной даты
to
События заканчиваются не позже указанной даты
page
Номер страницы (по умолчанию 1)
pageSize
Количество элементов на странице (по умолчанию 10)

Как запустить проект

Требования
Для запуска проекта необходимо:
.NET SDK 9
PostgreSQL

Настройка строки подключения
Перед запуском необходимо указать строку подключения в файле appsettings.json:
"ConnectionStrings": {
"DefaultConnection": "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=postgres"
}
При необходимости замените параметры подключения на свои.

Создание базы данных
Схема базы данных управляется миграциями Entity Framework Core.
Миграции находятся в проекте Infrastructure.
Создание новой миграции:
dotnet ef migrations add MigrationName --project EventManagementService.Infrastructure --startup-project EventManagementService
Применение миграций:
dotnet ef database update --project EventManagementService.Infrastructure --startup-project EventManagementService
При запуске приложения автоматически применяются все ожидающие миграции с помощью метода:
db.Database.Migrate();

Запуск

Клонировать репозиторий:
git clone https://github.com/kursksupport/YaPracticum
Перейти в папку проекта.
Запустить приложение:
dotnet run
После запуска в консоли появятся адреса приложения
Swagger доступен по адресу:
https://localhost:<порт>/swagger

Аутентификация и авторизация:
Для доступа к защищённым операциям используется JWT-аутентификация
В системе предусмотрены две роли:
'User' - обычный пользователь. Права: просмотр мероприятий и бронирований, создание бронирований, отмена только собственных бронирований.
'Admin' - администратор. Права: полный доступ к управлению мероприятиями, создание и просмотр бронирований, отмена любых бронирований.
Управление мероприятиями (POST /events, PUT /events/{id}, DELETE /events/{id}) доступно только пользователям с ролью Admin
Операции с бронированиями требуют аутентификации. При отмене бронирования обычный пользователь может отменить только свою бронь, а администратор любую.

Регистрация пользователя:
Для регистрации используется POST /auth/register
При регистрации необходимо указать логин, пароль и роль. Если роль не указана, используется User.

Получение JWT-токена через Swagger:
1. Запустите приложение 'dotnet run'
2. Откройте Swagger https://localhost:<порт>/swagger
3. Выполните регистрацию через POST /auth/register
4. Получите JWT-токен через POST /auth/login. В ответе API будет возвращён JWT-токен
5. В Swagger нажмите кнопку Authorize, Вставьте полученный JWT-токен в поле авторизации.

Настройка JWT:
Параметры JWT задаются в appsettings.json
"Jwt": {
  "Secret": "your-secret-key",
  "Issuer": "EventManagementService",
  "Audience": "EventManagementServiceClient",
  "ExpirationMinutes": 60
}
В репозитории и production-среде не рекомендуется хранить реальный секретный ключ непосредственно в appsettings.json.
Для production следует использовать безопасное хранилище секретов или переменные окружения. Значение Secret должно быть достаточно длинным, случайным и недоступным посторонним пользователям.

Запуск тестов
Для запуска тестов выполните команду:
dotnet test
Все юнит-тесты используют Entity Framework Core InMemory Provider, поэтому для их запуска PostgreSQL не требуется
Для запуска интеграционных тестов необходимо, чтобы Docker был установлен и запущен.
Контейнер PostgreSQL создаётся автоматически во время выполнения тестов

Обработка ошибок
Приложение использует глобальный middleware для обработки ошибок
Ошибки возвращаются в формате Problem Details (RFC 7807)
Возможные HTTP-статусы:
400 Bad Request
404 Not Found
409 Conflict
500 Internal Server Error
